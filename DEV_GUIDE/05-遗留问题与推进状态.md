### 为什么要验证它，而不是直接用？

`app/build.gradle` 第 89 行是 `implementation fileTree(dir: "libs", include: ["*.aar"])` ——
**全量引入、不解析传递依赖、不做版本仲裁**。这意味着两件事：

1. 只要 classpath 上凑齐了类，就能编过；但反过来，**凑不齐或类名/签名对不上，报错会以「找不到符号」形式炸在 App 源码里**，而不是提示「缺 aar」。
2. AAR 之间若有重复类（例如 `lib-common` 与 `lib-exoplayer` 都内含某些资源类），会在 merge 阶段冲突。

本项目 **16 个 Java 文件**硬引用了定制 Media3 包（`androidx.media3.mpvplayer`、`ui.danmaku`、`decoder.ffmpeg`、`decoder.av1`、`exoplayer.libass`、`datasource.rtmp`），集中在：

```
player/mpv/MpvUtil.java          player/mpv/MpvPlayerEngine.java
player/mpv/MpvPlayerEffect.java  player/exo/ExoUtil.java
player/exo/ExoSubtitleController.java   player/exo/ExoPlayerSession.java
player/exo/ExoMediaSourceFactory.java   player/subtitle/ExternalFont.java
player/PlayerManager.java        player/effect/audio/…   player/effect/video/…
ui/dialog/DanmakuSettingPanel.java      ui/activity/PlaybackActivity.java
setting/DanmakuSetting.java      service/PlaybackService.java
```

### 若编译失败，按这个顺序排查

| 症状 | 大概率原因 | 处理 |
| --- | --- | --- |
| `package androidx.media3.xxx does not exist` | fork 分支不对，非 `release-1.11.0-fongmi` | 确认 `fongmi-media` 分支；缺的模块补编后重新复制 |
| `cannot find symbol`（某个方法） | AAR 与 App 期望的 fork 版本 API 不匹配 | 对照 App 源码里调用的签名，换 tag/commit 重编该模块 |
| `Duplicate class` / `Entry name collision` | 两个 AAR 含同类，或 AAR 与 `libs.versions.toml` 依赖重叠（注意 `libs.rtmp.client` 是 `io.antmedia:rtmp-client`，与 `lib-datasource-rtmp` **不是**同一套） | 剔除重复的那个 AAR，或在 gradle 里 exclude |
| `Execution failed for ':app:merge…JniLibFolders'` | `lib-decoder-ffmpeg` / `lib-mpvplayer` 的 `.so` ABI 与 App `abiFilters` 不符 | 检查 App 是否只留 `arm64-v8a`+`armeabi-v7a`，与 media 模块的 `jniLibs` 对齐 |
| NDK 相关报错 | media 侧编过 ffmpeg native；App 侧不需要再编 | App 侧无需 NDK，若报缺 NDK 属异常，检查 `decoder_ffmpeg` AAR 是否已含 `.so` |

## 4. 等你拍板的决策项

### 4.1 `lib-*.aar` 要不要进 Git？

**背景**：`app/libs/.gitignore` 只有一行 `lib-*.aar` —— 上游刻意不入库，因为它们是编译产物。
但这带来一个现实问题：**任何新机器 clone 之后都编译不过**，必须重走一遍 media 编译（约 1 小时 + NDK 2.5GB）。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** 保持忽略 | 维持 `.gitignore`，把编译方法写进 `01 §4.4`（已写） | 仓库干净、符合上游约定 | 换机器要重编，约 1 小时 |
| B 直接入库 | 删掉 `lib-*.aar` 忽略规则 | clone 即可编 | 仓库一次性 +约 100 MB，且每次重编都会 diff |
| C Git LFS | `git lfs track "app/libs/lib-*.aar"` | 折中 | 需要所有人装 LFS，GitHub 免费额度有限 |

**当前默认走 A**（未改动 `.gitignore`）。如果你要让团队其他人能直接 clone 编译，告诉我切到 B 或 C。

### 4.2 `app/libs` 的其它 5 个 AAR 要不要源码化？

六个模块源码都在仓库里但不参与构建。是否要把它们纳入 `settings.gradle` 统一管理？
**建议不动** —— 它们是第三方闭源性质的解析库（含 `.so`），保持 AAR 形式最省心，改代码时按 §3-N 的临时流程处理。
